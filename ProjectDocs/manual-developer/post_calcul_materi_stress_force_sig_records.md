# post_calcul -materi_stress -force: the `*_sig` node_dof output records

The item names of the `post_calcul -materi_stress -force` family
(`-norx_sig`, `-nory_sig`, `-nors_sig`, `-shex_sig`, `-shey_sig`, `-shes_sig`,
the 2D `-mom*_sig` and the 3D `-mom1*_sig`/`-mom2*_sig`) as VALUE names of
`target_item` records against `node_dof_calcul`.

## Where

- `tochnog.h` / `tochnog-mod.h` (in sync): the enums `NORX_SIG` ... `MOM2S_SIG`
  (19 names), placed right after `POST_CALCUL_MATERI_STRESS_FORCE_AVERAGED_NODE`.
- `database.cc` (`db_initialize`): the name registration ONLY (no record:
  type/class stay default — the names are never used as record keywords).
- `miscel.cc` (`exit_tn`): the target resolution.

## How the names resolve

`target_item N -node_dof_calcul <node> -nory_sig` is parsed as
`ival = [ -NODE_DOF_CALCUL, <node>, -NORY_SIG ]` (the parser resolves
`nory_sig` through the name table). In `exit_tn`, `target_item[2] < 0` is
normally a DOF label (resolved via `array_member(dof_label, ...)`); when the
lookup fails AND the target record is `NODE_DOF_CALCUL`, the code falls back
to the position of the item name in the GLOBAL `post_calcul_names` array
(calcul.cc `calculate()`), which IS the slot of the item in the flat
`node_dof_calcul` layout. Not found → `db_error(TARGET_ITEM, ...)` (the guard
`number<0` was added; before, an unresolved negative name read `dbl_data[-1]`
— latent UB, no corpus test relied on it).

The item names are generated by the FORCE branch of `calculate()` in the same
order as the flat layout (2D: norx nory nors shex shey shes momx momy moms;
3D: norx nory norz nors shex shey shez shes mom1x ... mom2s), so the position
lookup is exact even when other post_calcul blocks precede the force block.

## The 2D plot direction fix (face tangent)

The plot components of the 2D family were drawn along
`reference_point - centroid` (one direction per element). The Professional's
force7/force8 give `nory == nors` EXACTLY for the vertical sections of the
cantilever even with the reference point at x=0 (its plot vector follows the
FACE, not the reference direction). The 2D contribution now computes the
per-face direction as the FACE TANGENT of the end face (the structure
thickness direction along the section), oriented TOWARD the reference point
(the sign convention measured on the Professional's force10, same as the 3D
decision). The moment arm of the section uses the same face direction (the
2D moment no longer carries the reference-point tilt twice). The quad9
middle-plane averaged nodes receive the mean of the two faces' plot vectors.

## Validation timing (pre-step blocks)

`control_mesh_*` records declared at their own control index (e.g.
`control_mesh_extrude 10` with `control_timestep 30`) make the control loop
run a `step_start(NO)+step_close(NO)` at index 10 — BEFORE the mesh changes
of the first timestep — and `step_close` calls `calculate()`, which ran the
element-type validation against the RAW (pre-extrusion) mesh. The element-type
check of `post_calcul_materi_stress_force_validate()` now runs only when the
current control index has a `control_timestep` (the final mesh); the
configuration checks (element_group, direction, reference_point) always run.

## post_element_force_normal

The record was registered as DOUBLE_PRECISION/MDIM (wrong per manual 6.935:
`index switch`). Now INTEGER with data_length 1. Consumed by
`post_element_force_calculate()`: with `-yes` only the elements on the
positive side of the section plane (plane through the middle, normal
`dir_normal`; the element CENTROID side test) contribute their internal
forces. Without the record, elements on both sides are used if present (their
internal forces cancel at the shared face — the force13 section at the domain
edge needs the `-yes` filter to see the load side).

## mesh_extrude quad9 -> hex27

`control_mesh_extrude` (mesh.cc `mesh_extrude`) now extrudes the quadratic 2D
elements: quad9 -> hex27 (9 base + 9 mid-plane nodes at the segment mid-height
+ 9 top nodes per layer — the Professional's force11 layout, measured on its
.dbs: node planes 0 / 2.5 / 5 / 7.5 / 10 for the 2-layer ring). The number of
layers comes from `control_mesh_extrude_n` (FIRST value; the z record gives
the total extent). The mid-plane and intermediate boundary nodes are NEW nodes
(the node-class records are copied from the source). The source quad9s are
deleted after the extrusion (like the tria3/quad4 sources). The layer
semantics of the LINEAR branches (tria3/bar2/quad4) are unchanged (layer
boundaries = the record values; only the last layer is non-degenerate — the
same convention as before, measured on the interface tests).

## npointmax default 27

The default of `number_of_integration_points` was raised from 9 to 27
(initia.cc): the hex27 needs 27 IP slots in `ELEMENT_DOF` (the record length
is `npointmax*nuknwn`). The element rules are unaffected (each element uses
its own npoint); the buffers are bigger. Measured bonus: beam3d (hex8) became
stable with the larger `ELEMENT_DOF`.
